# 图库性能审计与桌面化重构建议（实测）

> 历史测量记录，保留用于性能工作的对照。文中的行号、目录结构和部分故障已随清理改变；当前架构见 ../architecture.md，产品仅处理图片。

被测对象：旧版 `gallery_server.py`（2,343 行）+ `ui/` 7 个 JS + 本地缓存数据库与缩略图目录。
环境：Windows NTFS 机械硬盘，Python 3.12.10 + Pillow 12.2；服务运行在 8765。

## 0. 实测规模（与任务书不一致处）
- 顶层组 125 个；全部文件 215,553 个 / 1,544.5 GB；媒体 215,243 个。
- 图片 1,301 GB，平均 7.34 MB/张；94,149 张 >5MB，52,533 张 >10MB。
- gallery.db 41.8 MB，media 表 181,463 行；48 个组没有 media 行（合计 32,583 文件）。
- dedup.db 74.4 MB，phash 209,275 条，覆盖率 97.2%，147 个 folder（22 个陈旧）。
- thumbs 32,584 个文件 / 2.28 GB（12 GB 是上限，不是现值）。
- 400px 缓存命中率：随机 300 张 = 10.7%；某预热组前 200 张 = 14%。
- 任务书的 243,378 媒体、3.4 万缩略图与实测不符。

## 1. 冷启动：0.23s（DB 正常）→ 167s（全量重扫）
实测分解（OS 缓存已热）：
- import gallery_server 0.212s；只读打开 DB + 读 125 行 0.001s；125 组指纹 0.016s；14,357B meta JSON <1ms。
- 即 DB 指纹全部匹配时，启动到 bind 约 0.23s。
- 单组重扫：年年Nnian 5,243 文件 3.26s；黏黏团子兔 7,973 文件 6.32s；是阿朱啊 16,790 文件 5.28s。
- 全库 215,553 文件元数据遍历 166.8s。

为什么是 30-50 秒：
1. main() 顺序 init_db → get_warmer → scan_root → HTTPServer（gallery_server.py:2312-2321），扫描在 bind 之前，扫描期间 /api/ping 不存在。
2. VBS 固定睡 1.2s 就开浏览器；前端 boot() 先 fetch /api/state，失败显示断线，之后每 4s ping 一次（ui/90-shell.js:325-337,377-393）→ 启动延迟被量化成 4s 一档。
3. 指纹粒度是整组：_folder_fingerprint 统计组下每个包子目录 mtime_ns（gallery_server.py:434-451），包内增删一张图就让整组重扫 3-6s；几个大组就是 30-50s。DB 清空/首次运行 167s。
4. scan_root 无全局锁，2.5s TTL 过期后 /api/state 会重算指纹并重写 14KB JSON（16ms/次）。

结论：慢的不是 SQLite，而是把文件系统校验放在启动关键路径，且失效粒度是整组。

## 2. 首屏接口
- /api/ping 1.3-1.9ms，4B。
- /api/state 24.4ms，20,868B（125 组 + review）。
- /api/files 黏黏团子兔（7,966）18.0ms / 1,835,480B；二次 15.7ms。
- /api/files 是阿朱啊（16,780）首次 3.28s / 3,107,892B；二次 36ms（首次因指纹不匹配整组重建）。
- 无索引组（5,243 文件）磁盘遍历 3.3s 起。
- DB 路径成本：取 16,780 行 22.3ms + Python 排序 16.5ms + JSON 24.6ms ≈ 63ms，185B/行。
- /api/state 为拿 size/count 扫全部 125 组，数据本来就在 SQLite；无分页，一次 3.1MB。

## 3. 缩略图
缓存键 md5(realpath|mtime_ns|size|edge|quality)（gallery_server.py:570-577）；mtime 或视口宽度变化就整批 miss。
- 热 400px 1.6-2.5ms / 13-15KB；热 1600px 1.3-13ms / 121-154KB。
- 冷 400px：6MB 图 64-91ms；15-17MB 图 477-527ms。
- 冷 4200px：6-9MB 图 343-377ms（527-1,666KB）；15-17MB 图 1.02-1.05s（605-742KB）。
- 分布：<20KB 23,422；20-50KB 4,584；50-200KB 2,070；200-500KB 836；>500KB 1,672。
- 仅 1,672 张大预览，绝大多数 4200px 请求是冷的。
- 每请求固定开销：safe_media_path 两次 realpath + isfile；thumb_cache_path 对原图 os.stat（缓存命中也要 HDD 寻道）；dedup_index 首次还要 stat + SQLite SELECT。
- previewEdge 用精确视口宽度×DPR（ui/00-core.js:28-33），无量化 → 窗口一变整批缓存失效。

## 4. 前端
1080p（侧栏 360，CARD_STEP 214，ROW_STEP 250）：7 列 × 8 行 ≈ 56 张封面；2560 宽约 80 张。
- 热缓存 48 张 / 6 长连接 0.12s；加绘制约 100-200ms。
- 冷缓存 48 张干净复测（6 线程、进程内同路径）：2.47s，首张 0.25s、第 6 张 0.53s、第 24 张 1.29s，每 100ms 到 2-3 张（持续细流，非整批）；加 HDD 随机读 300-400MB 后约 3-6s。此前 5.61s 读数跨在服务重启上，已作废。
- openFolder() 先 await /api/files 再建墙（ui/90-shell.js:84-106）：冷组 3.3s API + 3.1MB JSON + 3-6s 封面 = 6-9s 空白。
- 单张视图：4200px 预览 0.35-1.0s/张，preloadAround 再拉前后各 2-3 张（40-view.js:187-202），首屏 1-3s。
- 无骨架屏/低清占位；冷加载是一片空框。
- loadDedup 86ms、loadHusk 7ms 并行，影响小。

## 5. 审计期间的运行环境故障
- 8765 最终由 PID 42956（WorkBuddy Python 3.13.12 pythonw）占用，/api/state 返回 thumb:false。
- 该实例没有 Pillow：所有未缓存 /thumb 返回 500 {"error":"thumb failed"}；_placeholder_jpeg() 无 PIL 时返回 b""，连灰块都没有。
- 早先 PID 46392（Python312 + Pillow）提供了第 1-4 节数据。
- 启动脚本硬编码 Python312，但 PATH 上的 pythonw 可能是别的版本；桌面化必须把 Pillow 作为硬依赖并自检/打包。

## 6. 重做必须改的设计（按收益）
P0
1. UI 先起、扫描后置：0.3s 内可交互，首屏只读 SQLite，文件系统校验放后台。当前 scan_root 在 bind 前是 30-50s 体感的直接原因。
2. 一次建全量索引：215,553 文件 / 167s 仅首次后台跑完，之后 /api/files 100% 走 SQLite（18-63ms）。
3. 封面预生成：索引时一次解码同时出 400/1600，冷墙 3-6s → 0.1-0.2s；当前 400px 覆盖仅 10.7%。
4. 失效粒度改为按文件 (size,mtime) diff 或 ReadDirectoryChangesW，避免包内加一张图重扫整组。
5. 桌面端别走 HTTP 取缩略图：自定义协议/本地文件，去掉 realpath 校验和 HTTP 头；把 (path,size,mtime) 存 DB，避免每张封面 stat 原图。

P1
6. 预览尺寸量化 1600/2400/3200/4200，窗口 resize 不再整批 miss。
7. 缩略图任务队列：少量 worker + 可见优先 + 有界队列；6 路并发在 HDD 上放大寻道；prewarm 每张 sleep 0.03s（上限约 20 张/s，全库 8 小时）。
8. 不要传 3.1MB 整组 JSON：按包/分页，或进程内查 SQLite。
9. SQL 层排序 + 复合索引；media 的 idx_media_folder 与主键前缀重复，可删。
10. 预览内存按字节限额（8×4200px 约 260MB）。

P2
11. 缩略图分 256 子目录（32,584 文件挤一个目录，枚举 84ms）。
12. 解码失败必须有灰块占位；HAS_PIL=false 启动时就报错，不要静默降级。
13. /api/thumb/stats 全目录扫描 84ms，可维护计数。
14. 删掉 /api/state 的 2.5s 扫描，改 SQLite + 文件监听增量更新。

## 7. 预期收益
- 冷启动到可交互：0.23s（正常）/30-50s（指纹失效）/167s（全量）→ <0.3s 恒定。
- 打开冷组 5,243 文件：3.3s + 3-6s 封面 → 20-60ms + 0.1-0.2s。
- 首屏 56 张：3-6s 冷 / 0.12s 热 → 0.1-0.2s。
- 4200 预览：0.35-1.0s/张 → 看过的组 2-10ms。
- 缩略图单请求：1.6-2.5ms → 约 0.1-0.3ms。
