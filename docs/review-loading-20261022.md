# 图片加载优化 Review 与实测

日期：2026-10-22。范围：同卷源图读取、预览编码、前后台解码预算和预热暂停。基础版本为 794abdd，保留现有 API、pHash 算法、渲染质量、缓存键和正式界面。

## 实现与 Review

- 原实现从等待解码预算到缩放、编码和写缓存一直持有源卷名额，两个 worker 在同卷实际上串行工作。现在只在读取图片头和物化首帧时占用源卷；解码预算覆盖缩放、颜色转换和编码，先关闭图像再归还预算。
- 同卷仍一路读取、全局最多两路解码、512 MiB 估算预算，前台等待者优先于后台。pHash 构建在源卷名额外等待解码预算，算法未变。
- 读取图片头前检查源文件版本，等待预算后再次检查，避免把等待期间变化的内容写入旧缓存键。
- Review 发现暂停预热可能长期占用生成锁或解码预算；已改为图片边界暂停，处理中仅检查取消。等待生成锁可取消，暂停不会把看图资源扣住。
- 没有改数据库 schema 或扩大队列，不预先解码全库图片，不使用真实图库做删除和压力测试。

## 同素材对照

新增 scripts/benchmark_pipeline.py。固定随机种子和 ICC 日期，生成普通 JPEG、EXIF 旋转 JPEG、带 ICC 的透明 PNG、静态 WebP、GIF 动图及 WebP 动图，各四份，共 24 张临时图片。源图放在 F:，独立临时数据与派生缓存放在 C:。

两组对照采用先旧后新、再新后旧的顺序，旧实现复测从 git archive 导出的 794abdd 运行，不切换共享分支。各组 source_manifest 完全相同，800/1600/2560 档共 72 份预览 SHA-256 完全相同。

| 场景 | 原实现，两轮 | 优化后，两轮 |
|---|---|---|
| 四路首次 800 预览，总耗时 | 2.80 / 2.85 s | 2.42 / 2.38 s |
| 四路首次 800 预览，P95 | 609 / 631 ms | 560 / 601 ms |
| 后台预热期间四路 2560 预览，总耗时 | 6.63 / 7.09 s | 5.57 / 5.61 s |
| 后台预热期间四路 2560 预览，P95 | 1355 / 1393 ms | 1244 / 1293 ms |
| 四路热 1600 预览，P95，72 次 | 31.48 / 36.43 ms | 36.23 / 32.80 ms |
| 负载期间健康接口，P95 | 2.02 / 2.02 ms | 3.16 / 2.10 ms |
| 负载期间图片清单，P95 | 23.03 / 21.80 ms | 21.94 / 21.15 ms |
| 后端 RSS 峰值 | 243.0 / 244.7 MiB | 294.9 / 297.0 MiB |
| 后端结束时 RSS | 73.1 / 72.9 MiB | 73.2 / 73.2 MiB |

四路首次预览总耗时减少约 13%–17%，预热期间前台加载减少约 16%–21%。并行度的实际提升带来约 52 MiB 的峰值内存增加，结束后释放；热预览性能接近，没有宣称所有请求都更快。

原始报告保留在 output/pipeline-before-fixed.json、pipeline-after.json、pipeline-after-repeat.json、pipeline-before-repeat.json。更早的 pipeline-before.json 生成的 ICC 日期未固定，不参与同素材百分比和输出一致性计算。

这里的首次指派生缓存未命中，没有冲刷 OS 缓存。进程 IO 不代表物理磁盘 IO，后端 RSS 不包含 Electron。每个首次场景 24 个样本，属于本机重复实测，不代表全部真实素材或机械盘绝对冷读；未把它当作整夜运行或巨大动图验收。
