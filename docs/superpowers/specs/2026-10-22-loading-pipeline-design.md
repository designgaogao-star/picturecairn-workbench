# 图片加载流水线优化

## 目标与范围

用户已要求继续提升产品质量。本轮落实既定的浏览优先原则，改进同卷连续加载和后台预热期间的资源调度。保留现有界面、API、图片输出规范和缓存键，不增加功能或更换技术栈。

## 调查与方案

目前预览生成在获取源卷读取名额后，持有该名额等待解码内存、缩放、颜色转换、编码和写入 SSD 缓存。两个前台 worker 在同卷上实际串行完成这整段工作。解码内存虽然有上限，但等待时没有前后台优先级。

可选方案：增加 worker 会放大内存和磁盘竞争；预先生成全库预览会增加启动与缓存成本；拆分现有加载阶段则能沿用资源上限并缩短读取名额的占用。本轮选择第三种。

1. 在源卷名额内读取图片头和元数据，随后释放名额。
2. 等待全局解码预算，前台请求排在等待中的后台任务之前。等待不持有源卷名额。
3. 重新取得源卷名额，核对文件版本并物化首帧；关闭源文件后释放名额。
4. 在解码预算内进行方向处理后的缩放、颜色转换与编码，完成后关闭全部图像对象并归还内存。
5. pHash 构建也遵循先等解码预算、再取得源卷名额的顺序；计算规范不变。

同卷仍只有一路源文件读取，最多两路解码、估计内存 512 MiB。前台不能抢断已在执行的 Pillow 原生调用，但下一次预算分配优先服务前台。缓存命中继续直接返回缓存。

预热暂停在图片边界生效；持有生成锁或解码预算期间只响应取消，不等待继续。等待生成锁时可以暂停和取消。Review 用回归确认暂停不能长期扣留解码名额。

## 验收

- 用事件控制编码阶段，证明第一张编码未结束时第二张同卷图片可以加载；首张的内存名额仍被保留。
- 预算耗尽时，等待图片解码不妨碍同卷前台读取；前台解码等待者优先，取消等待不会泄漏名额。
- 方向、透明度、首帧、元数据、坏图、缓存版本和 pHash 既有测试通过。
- 固定种子的临时混合图库分别运行改动前后基准：串行首次预览、四路首次预览、后台预热竞争、热缓存，以及健康接口和列表响应。报告标明没有清空 OS 缓存，进程 IO 不是物理磁盘 IO。
- 比较同素材同尺寸输出 SHA-256；渲染结果无变化时保持现有缓存版本。
- 完成源码、类型、契约检查，使用唯一构建入口生成桌面包并验证实际 HTTP 和 Electron 流程。真实数据不参与删除或压力测试。

## 不在本轮

不承诺机械盘绝对冷读、整夜运行或任意巨大动图均已完成压力验收。不修改真实旧数据库，不预热全库，不删除 prototype，不推送 Git。
